# Base-2与学校人物美术的分工

## 产品定位

Base提供人物编辑与行动逻辑，学校学生会提供自己的美术。继续采用简单的部件搭配，不扩充通用成品美术库，不做精细捏脸、布料模拟或复杂表情。

| 由Base提供 | 由学校与续建Agent提供 |
| --- | --- |
| 部件槽位、可选颜色、组合兼容性与预览逻辑 | 人物风格、校服、发型、服饰、贴图与校方认可的装饰 |
| 统一骨架与站立、行走、挥手；导航和到达判断 | 按骨架制作和绑定的模型，以及美术源文件 |
| 服务端账号/学校隔离、配方存档、版本冲突、刷新/重登恢复 | 作者、来源、商用/修改/再分发许可和素材版本 |
| 背包、轻道具、非破坏性互动、数量与权限校验 | 经负责人审核的学校展示风格与新素材上线决定 |

包内现有原创人物是能启动的占位与技术样例，也用于旧存档兼容。新方向不会删除历史目录或强制替换已有用户形象；它们不代表学校最终美术，不再以增加其款式为交付目标。

## 素材槽位和约束

槽位沿用 `body`、`hair`、`top`、`bottom`、`shoes`、`glasses`、`accessory`。完整目录和实际骨架以 `assets/avatars/*/catalog.json`、`src/avatar/library-m2.mjs` 及对应生成器为准，不凭文档猜节点。采用米制坐标和 `campus-humanoid-1`；完整人物预算为22,000三角面、90渲染批次、1.6MB GLB，角色换美术不改变权威碰撞体、移动速度或互动距离。

当前运行时使用受控目录与确定性生成器。**把任意GLB、VRM或PNG放进文件夹并不会自动成为可用人物。** 新学校模型需要由续建Agent实现相应的目录/生成器适配，并验证刚性部件绑定或明确实现蒙皮适配。当前没有因此新增“任意人物一键上传发布”后台接口。

每项新素材记录稳定部件ID、槽位、版本、骨架版本、文件大小与SHA-256、作者和许可。禁止用同一ID/版本覆盖不同网格；保留旧目录与生成器。需要升级时发布新目录，通过明确的迁移确认处理缺失/不兼容部件，不能静默重置存档。

## 续建流程与验收

1. 先用占位人物确认编辑、保存、重登和空间移动可用，再复用学校风格或收集一份人物参考。
2. 先做一件上装或一个发型，登记来源和许可。二维生成图是设计稿；完成三维建模、骨架适配后才能验收运行效果。
3. 在独立学校测试实例接入一个新目录/生成器，验证站立、行走、挥手、穿插、兼容性、性能预算和素材摘要。
4. 保存搭配，刷新、退出重登、在另一个独立浏览器上下文恢复；进入空间，确认显示摘要与存档一致，导航、碰撞和道具规则不受美术影响。
5. 同时验证一个旧配方仍可精确重建，错误或缺失素材明确拒绝。校方负责人审核后再决定上线与迁移；发布和回滚步骤由续建Agent落实到该学校项目，不能仅凭生成截图标记完成。

直接使用 `prompts/05-AVATAR-LIBRARY.md` 交给Agent续建。无需先扩展Base的通用美术数量。人物设计源文件、学校专有素材和测试用户数据保持在学校项目与私有输入中，未经授权不打入公开通用包。
