## Default onboarding for a user who only uploads the ZIP

用户只上传本包并问“这是做什么用的？怎么用？”（或相近问法）时，自动进入本节流程。不要要求用户复制 prompts、先看文档、填写技术表格或自己运行命令。

1. 在可读文件环境解压/检查包，读取 `AGENT-START.md`、`START-HERE.md` 和 `docs/AGENT-ONBOARDING.md`，用用户的语言解释用途和下一步。无法解压时如实说明缺少文件能力，请用户解压或换到能读文件的 Agent；不能声称已读包。
2. 首次说明保持简短：这是供学校搭建可参观超维空间的底座，包含场景、A2A、接待与自有资料知识库；用户提供平面图/草图、公开资料和美术后，可由你逐步搭建。由你负责读文档、检查环境、运行命令和验证。
3. 只问一个当前选择：“你想先看示例，还是直接搭建自己的学校空间？有平面图可以一起上传。”已有学校目标、图纸或明确指示时直接使用，不重复索取。
4. 用户说“先看示例/帮我启动”后，检查环境与现有服务，按 `docs/STARTUP.md` 启动独立示例并给出地址。收到“搭建学校”的目标或图纸后，自动读取 `prompts/00-BUILD-SCHOOL.md`，把它作为你自己的执行清单，按缺项渐进收集资料并推进；用户不必再贴长提示词。
5. 只解释用途的问句先触发读包与引导。用户选择启动或搭建后执行对应工作，不预先替用户选择学校、改源码、安装第三方软件或连接数据库。缺少模型密钥、正式美术等不会阻断独立的建模和资料整理；需要它们时再说明具体缺项。
6. 在学校项目的 HANDOFF.md 记录输入、已完成项、下一步和未核实项，续聊时先复用。遵守本文件后续的权限、来源、数据保护和真实验收边界。
7. 结构场景跑通后，主动说明下一步可做美术升级，自行读取 `prompts/04-VISUAL-POLISH.md`。按校园清爽、温暖手绘或轻科幻等可理解的方向引导用户，协调素材、灯光、标识、家具和展示界面；用户要求可展示版本时，不把简陋体块当最终视觉交付。已有风格直接复用，用户暂缓美化则在交接中记录下一步。

`AGENT-START.md` 是无需用户提示词的发现入口；`docs/AGENT-ONBOARDING.md` 含首次回复示例与后续分支。此约定依赖接手 Agent 能读取并遵循包内文件，不是 ZIP 自己执行的程序。

## Development contract

Read README.md, docs/PROTOCOL.md, docs/AGENT-WORKFLOW.md and docs/ARCHITECTURE.md before changing a contract. Run npm run doctor, npm run build, npm test, npm run verify and the relevant browser/A2A checks. Report real results, input assumptions and limits.

- Base is application neutral. Schools, artwork, rooms and reception knowledge live in space packages; never hard-code school IDs or room counts in the core.
- Keep stable spaceId, sceneId, entityId and agentId. The server validates capabilities, access, positions and side effects. A model reply grants no permission.
- Public reception reads published knowledge only. Never expose private documents, .local credentials, API keys, input PDFs or other tenants' data to the model or public routes.
- School knowledge uses the existing PostgreSQL/pgvector implementation (PGlite locally or a PostgreSQL server). Filter publication before embedding, scope every query by space, preserve source revision and transactionally replace reviewed snapshots. Do not substitute an untested mock vector store or copy personal databases into the universal package.
- Preserve request identity across retries. A repeated request with altered content is a conflict. Keep receipts and task status across restarts.
- Image interpretation is a documented Agent step. Record measured dimensions, inferred geometry and unknowns. A generated mesh without a walkable runtime is not acceptance.
- Every generated model retains a reproducible build script, interpretation input and provenance. The renderer, navigation and room interactions must share one geometry source.
- Uploaded user drawings remain in .private-inputs and projects (ignored). Public source packages contain only original synthetic examples. Do not publish or bundle private drawings without explicit authorization.
- Do not call deterministic knowledge lookup a live LLM run, browser automation a human test, or one-host processes physical cross-device acceptance.
- Do not start the old game's development, minigame fixes or long acceptance suites.

Use Node 22.13+ or 24 LTS, parameter arrays for processes and ordinary writable directories on Windows/macOS. Do not clear existing data or terminate unrelated processes. No production runtime dependency on the old game is allowed.

For the authorized M1 extension, read M1-START.md, docs/M1.md and evidence/m1/ACCEPTANCE.md. Preserve every sealed Base/M0 package and existing runtime. Applied database migrations are immutable; add a new version rather than edit one already recorded. School/organization authorization, last-owner protection and audit remain server-side. Never use invitation acceptance to overwrite an existing membership. A full backup requires stopped writers and integrity checks; restore only into a new directory/database namespace. M1's current priority slice does not authorize expanding into minigames or silently claiming real SMTP delivery, production readiness, full M1 messaging or M2-M5 completion.

The subsequent M1 communication scope is documented in M1-SOCIAL-START.md and docs/M1-SOCIAL.md. Keep Nakama message body authority, Base metadata/ACL/receipts, NodeBB native edits and their separate licenses. New service tests require HD_M1_TEST_FIXTURE=1 and dedicated fictitious data. SSE must re-check identity and scope on every batch, including existing connections. Never grant school managers blanket DM reading; reported-message review needs a specific report, scoped privilege and recorded reason. Preserve message revisions and source-operation recovery. Validate server backup/restore with the new message tables and native bodies. Read evidence/m1-social/ACCEPTANCE.md; avoid expanding this scope into M2-M5 or claiming a target-server deployment that has not occurred.
