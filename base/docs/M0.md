# M0：校园身份、人物存档与论坛贡献链路

> **历史范围 / 兼容工具参考。** 本文记录当时里程碑，不是当前完成度或开发优先级。旧的“尚未实现”、功能上限、数据库数量及候选状态不覆盖后续版本；涉及具体命令仍须核对当前脚本和实例。当前流程以[统一开发手册](../DEVELOPMENT-MANUAL.md)及本版验收为准。

## 1. 本阶段交付范围

面向 **Ubuntu 服务器 + 浏览器前端**。这是对四个 Base 规划的第一阶段实现，不表示 Base-2/3/4 全部完成，也不是已部署到公网的生产服务。

新增入口为 `/m0.html`，原空间入口为 `/?space=<spaceId>`。原 Base v0.2.1 封存包、私有图纸、学校项目和访客数据不迁移、不覆盖。M0 在独立开发工作树、数据库命名空间和数据目录运行。

| 链路           | 实现                                                                                                                                                                                 |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 账号与学校隔离 | Keycloak OIDC 授权码 + PKCE、state/nonce；稳定 issuer/sub → Base userId；每校成员角色与撤权；映射 Nakama/NodeBB 账号。学校来自服务端成员表，客户端不能选择或伪造权限。               |
| 人物编辑到恢复 | 9 类原创小样选项，带版本的配方，确定性 GLB、行走/招手动画；写入 PostgreSQL；重复请求回执、乐观并发版本检查；原空间渲染器加载同一个 GLB；重新登录、第二浏览器上下文、服务重启后恢复。 |
| 论坛审核到计分 | 实际 NodeBB 待审队列与发布/删除；带源 ID、版本、操作者、学校的事件；PG 贡献账本 + 同事务 outbox；Nakama 服务端权威榜单；重复事件去重、撤回冲正与投影重建。                           |

贡献规则 `m0-content-accepted-v1` 仅为虚拟样例：采纳 +10，撤回 -10。用户的旧运营材料到位后另行配置正式规则。帖子、聊天和模型回答不会直接自动计分，也不会自动进入公开知识库。

## 2. 选型决定

实际版本、源码提交、下载哈希与许可证固定在 `integrations/versions.json`；Base 和 NodeBB 分别保留锁文件。

| 部分                        | 决定与集成边界                                                                                                                                                                                    |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Keycloak 26.8.1             | 选用。浏览器实际走 OIDC 授权码 + PKCE，API 验证 RS256、issuer、audience；模拟账号的密码授权仅供 M0 自动验证，正式环境关闭。                                                                       |
| PostgreSQL 18.6             | 选用。Base 业务库为权威；IdP、每校论坛、每校 Nakama 各用独立数据库和角色。初始化工具生成不同密码，拒绝覆盖既有命名空间。已有 pgvector 接待模块保持原实现。                                        |
| Nakama 3.41.0               | 选用账号映射、私有存储权限验证与榜单。普通客户端不能写贡献分；认证须兑换 Base 的短期一次性票据，原生账号/存储读取仍检查学校资格。聊天等未集成端点在 M0 关闭。                                     |
| NodeBB 4.16.3               | 选用独立论坛服务。M0 使用小型 GPL 桥接插件，走实际队列、审核、发布和删除；读取原生页面必须有本校会话。M0 原生写 API 与 WebSocket 关闭，避免第二条写入路径绕过审核事件。完整原生编辑体验后续集成。 |
| CharacterStudio             | 本阶段不引入。固定提交的 CharacterManager 直接引用钱包、NFT 和购买模块，且运行需要独立素材包；完整运行兼容及素材授权没有通过。本阶段选择原创轻量编辑器，不把候选应用说成已集成。                  |
| Three.js 0.186.1 / glTF 2.0 | 选用，直接兼容现有空间渲染器。原创部件、模型生成代码均为 MIT。three-vrm/VRM 是后续可加的适配格式，本次没有冒充 VRM 集成。                                                                         |
| PostgreSQL outbox           | M0 已实现并验证重试和重建。pg-boss 保留为 M1 候选，没有把自写轮询称为已接入 pg-boss。                                                                                                             |

NodeBB 上游依赖经审计后固定修补：sanitize-html 2.18.1、sharp 0.35.5、lodash 4.18.1、fflate 0.8.3。修补命令在 `tools/m0-patch-nodebb.cjs`，完整解析版本在 `integrations/nodebb-upstream/package-lock.json`。交付结果记录审计时点，不保证未来不会出现新公告。

## 3. 目录与数据归属

```text
src/platform/             身份校验、成员权限、业务数据库、贡献/outbox与服务适配
src/avatar/model.mjs      原创部件目录、配方校验、确定性 GLB 与动画
database/m0.sql           追加式 M0 表；不读取旧 .local/state.json
public/m0.*              浏览器登录入口、人物编辑、记忆投稿/审核、贡献榜
integrations/nakama/      认证/权限钩子、服务端榜单投影
integrations/nodebb/      独立 NodeBB 插件源码与 GPL LICENSE
integrations/nodebb-upstream/  修补后上游依赖锁文件
integrations/versions.json     固定服务版本、下载来源及校验值
tools/m0-*                安装、初始化、启动/停止、虚拟账号、数据快照
tests/m0-*                真实服务集成与独立浏览器验证
qa/m0/                    当前环境验证产物（开发生成，不是用户资料库）
```

`hd_users` 只按已验证的 issuer/sub 建立唯一映射；学校资格是 `hd_memberships`，不从邮箱域名或昵称推断。`hd_avatars` 按学校 + userId 存储版本配方和模型哈希。`hd_events` 保留源事件；`hd_contributions` 为追加账本，撤回引用原加分流水；`hd_scores` 和 Nakama 是可重建投影。

事件是 `hyper-dimension.event/v1`，包括 eventId、schoolId、source.system/id/revision、actor、subject、status、visibility、period、occurredAt。Base 只从配置中的可信论坛端点拉取；浏览器没有提交任意计分事件、操作者或分数的接口。

论坛正文与队列由 NodeBB 持有；Base 保存源引用和账本。M0 论坛事件保存在源服务，再由轮询对账；Base 账本和 outbox 同事务提交。跨服务采用至少一次投递与幂等，没有分布式事务保证。

## 4. Ubuntu 安装与启动

这是 **M0 本地/测试环境** 的已验证运行方式，默认只监听回环地址。正式公网部署还需要 M1 的 TLS、域名、反向代理、非 root 运行、备份策略与运维配置，不直接暴露开发模式。

### 前置条件

Ubuntu，Java 21，PostgreSQL（本次实际为 18.6），curl、git、tar、xz-utils、sha256sum、PostgreSQL 客户端；初始化本项目时已有 Node 22.13+ 或 24。服务安装器会另外下载并校验 Linux x64 Node 24.22.1。

在全新的服务目录执行，不要使用旧 Base 的数据目录：

```bash
npm ci --ignore-scripts
npm run setup
bash tools/m0-install-ubuntu.sh /srv/hyper-dimension-m0-services
export PATH=/srv/hyper-dimension-m0-services/node/bin:$PATH

# 通过受控环境变量提供数据库管理员连接，不提交到 Git，也不把密码贴入命令输出。
# 管理员仅供初始化建库。常驻 Base/论坛/Nakama/Keycloak 都使用各自普通角色。
export HD_M0_PG_ADMIN='<private PostgreSQL admin connection URL>'
node tools/m0-init.mjs --runtime /srv/hyper-dimension-m0-services --namespace hdm0_trial --fixtures
unset HD_M0_PG_ADMIN
export HD_M0_CONFIG=/srv/hyper-dimension-m0-services/private/config.json
node tools/m0-services.mjs setup
node tools/m0-services.mjs start
```

另开终端，在源码目录：

```bash
export HD_M0_CONFIG=/srv/hyper-dimension-m0-services/private/config.json
export HD_M0_USERS=/srv/hyper-dimension-m0-services/private/test-users.json
node tools/m0-seed-fixtures.mjs --allow-fixtures
```

打开 `http://127.0.0.1:4280/m0.html`。虚拟用户 alice 属于 north，bob 属于 south；moda/modb 是各自学校审核者，shared 属于两校。密码由初始化随机生成，只在 `private/test-users.json` 中。接手 Agent 可在本机帮助读取或重置这些**测试账号**，不能将私有配置封入公共包。

`--fixtures` 仅用于隔离验证。它开放测试 client 的密码授权；浏览器仍走 PKCE。去掉该参数会生成没有测试账号的实例，不能假装学校正式账号和找回流程已上线。正式学校接入在 M1 完成。

在 WSL 环境，启动器已加入 Java 的 IPv4 配置，避免 Windows 浏览器无法访问 Java 监听的 IPv6 映射回环端口。当前验证由 Windows 的独立 QA 浏览器访问 WSL Ubuntu 服务，不能称为物理多设备或真人验收。

### 启停与日志

启动器检测端口占用，验证必需的论坛插件文件与源码一致，启动后核对两校原生接口确实拒绝未登录访问。必需子服务退出会停止其余本次启动的子服务，不终止已有服务。

`Ctrl+C` 停止当前启动器；或另开终端使用同一个私有配置执行：

```bash
node tools/m0-services.mjs stop
```

日志和本次进程记录位于服务目录的 `logs/`。停止工具检查进程归属，PID 不匹配时拒绝操作。`private/`、数据库、数据目录和备份都需要保留，不能作为构建缓存删除。

## 5. 验证与验收

```bash
npm run doctor
npm run build
npm test
npm run verify
npm run test:m0

# 使用另建的 QA 浏览器，不读取用户浏览器或个人 profile。
export HD_QA_CHROME='<owned QA Chromium/Chrome executable>'
npm run test:m0:browser
```

集成测试使用真实 Keycloak、Nakama、NodeBB 与 PostgreSQL，不用内存替身通过验收。其固定账号可重复验证；论坛的既有新人限流保留，重复测试先等待已存在的冷却期，不降低限流或放宽业务断言。网络断开是明确标记的 outbox 故障注入。

M0 性能范围固定为两校、五个虚拟账号、原始样例建筑和小型原创人物；不宣称大并发承载。暖机 50 次读取、5 并发的本机 API P95 目标为 500ms；实际值由 `tests/m0-metrics.mjs` 输出。软件渲染的浏览器截图不作为真实 GPU/移动端帧率报告。

验收与完整规划用例的映射：AC-05 的稳定三系统映射、AC-06 的两校访问/撤权子集、AC-07 的论坛事件子集、AC-12/13/14 的人物小样链路、AC-21/23 的桥接论坛链路、AC-26/27 的记账/冲正/重建。组织/合作方角色、完整素材目录、完整论坛功能与全量恢复不因此标记为完成。

## 6. 备份与恢复

本次用 `pg_dump -Fc` 备份 **M0 业务库**，还原到新的隔离数据库，再对账号、成员、映射、人物、回执、论坛事件、账本和分数九张表逐表核对行数与 SHA-256。源库不覆盖。重启前后也使用同样的快照核对。

正式整套恢复需要同时备份/对账 Keycloak、每校论坛、每校 Nakama 数据库、Base 的 A2A JSON 数据目录、私有密钥和配置；本阶段没有把单个业务库恢复说成六库和所有外部系统完整灾备。旧 Base 数据的迁移方案在 M1 单独制作，迁移前必须备份与对账。

## 7. 明确保留到 M1/M2 的工作

- M1：学校正式入驻与账号找回、访客账号绑定、组织与委托权限、撤权交接的完整角色矩阵；A2A JSON 状态迁移、审计/保留策略、全套备份恢复。
- M1：NodeBB 原生写入/编辑与完整事件覆盖。当前 M0 只开放桥接审核流程；崩溃若发生在 NodeBB 原生发布和桥接事件保存之间，需要对账，不应盲目重提。本阶段没有证明任意位置断电的跨系统原子性。
- M1：私信、通知、聊天逐包权限、正式 outbox 运维与告警；当前未验证的服务端点保持关闭。
- M2：正式人物风格和完整部件数量、资产授权目录、VRM 适配（按实际需要）、背包、轻道具与动画品质。现在是可编辑/存档/运行的原创技术小样。
- M3/M4/M5：地图记忆深度联动、活动/志愿流程、正式运营 timeline 与规则、奖励和合作方业务，依照已批准规划后续开发。

完成 M0 后不自行展开这些阶段，也不恢复旧游戏开发。
