# 接待会话与校园连接 · v0.8.0

## 产品边界

Base 不托管用户的个人 Agent 长期记忆。用户自带 Agent 自行管理其本机记忆。本服务仅管理网页接待的会话与学校业务数据；接待会话、私信、预约问题和私人资料不会自动写入公开 RAG。

### Base-1：页面接待

- 用户/学校/接待 Agent 各自隔离，随机 contextId；登录用户从服务端身份取得 owner，匿名独立示例使用签名访问 Cookie。相同会话不能被其他用户、学校或 Agent 复用。
- 会话持久化到现有 PostgreSQL 权威状态；独立示例兼容文件存储。一个 session 是记录，没有每人一份常驻模型/进程。模型并发最多2、等待队列最多16；同一会话有未完成回答时拒绝另开并发轮次。
- 当前沿用单写进程及事务JSON状态快照，尚未验证千人负载或横向扩展；正式容量须在目标服务器用预期同时在线人数、会话量和模型延迟压测后确定。新增session不等于无限容量。
- 默认从创建时间保留30天。学校负责人在 `/reception-admin.html` 配置1–365天、会话数、轮数和上下文轮数；管理员可查看不含正文的数量/状态并清理到期记录。期限调整只影响新会话，已有会话显示自己的到期时间。模型每轮只取最近有界上下文（默认4轮），学校事实仍按当前发布源验证。
- 空间右侧支持新建、切换、继续、JSON导出、删除。导出是本人的历史记录，不能当作当前学校政策。删除清除正文/结果/历史缓存，在途回答落库前再次验证状态；重放旧 messageId 不会复活对话。
- 启动/恢复时先做保留期限清理，此后每60秒清理；请求读取也校验期限。兼容历史会话采用原创建时间，不重置为今天。最小墓碑和请求摘要用于防重放，保留在权威状态；不把墓碑当作对话正文。
- 删除不会追溯擦除已导出的文件、数据库WAL、离线备份。学校必须配套备份保留/销毁政策；恢复后的到期正文会在服务开放前清理。日常不需要为每个访客启动本地 Hermes。

### Base-2 与 Base-3：发现名片

人物私人资料及部件搭配保持原有存档。新增独立的发现名片，默认不加入；本人明确同意提交公开昵称、院系、届别、城市、介绍、兴趣及愿提供支持的意愿。审核后仅向本校有效成员展示，身份/履历仍标为本人自述。修改立即转为待审并停止展示；本人退出、管理员下架、成员失效或绑定地点不再公开时，目录/点位入口受当前状态约束。

页面 `/network.html?school=学校编号` 支持目录筛选、本人编辑、审核/驳回/下架；联系仍走已有联系人同意及 Nakama 私信，不公开电话/邮箱，也不自动创建联系授权。

### Base-3：学长/导师支持

仅已发布且自愿提供支持的人可开放时段：主题、UTC开始/结束、1–20人容量、可选公开地点。双方通过申请→支持人确认/拒绝→取消/完成；完成需场次已结束。拒绝自约、重复活跃申请、支持人时段重叠、学生预约重叠及容量超卖，事务锁和回执防并发/重复写入。

预约问题仅向双方展示。学校负责人/管理员协调视图仅提供状态、双方、场次时间及操作原因，可取消场次或预约，不获得任意问题正文读取权。关闭时段、名片修改/退出会取消未完成预约，产生不含问题正文的站内通知。此处不自动发外部会议、收款或代传个人资料。

### Base-3 与 Base-4：职业与机会

实习、岗位、奖助、项目、经验交流、咨询六类卡片。正文和讨论在原生 NodeBB；Base 保存来源编号、组织范围、类别、面向对象、截止日期、官方HTTPS申请入口与地点。先在论坛提交正文，再在校园连接页面绑定卡片。

卡片须同时满足：正文当前已发布、结构化信息审核通过、审核绑定的正文版本仍一致、未撤回、未到期及当前学校/组织权限有效。变更链接/截止/元数据会重新待审；正文版本更新后需重新核对卡片。普通作者可修改/撤回；学校或有权组织的负责人/管理员可核对、下架及维护截止时间，操作留原因、版本与审计。收藏只在本人账号下保存；外部申请由用户自行点击，不代投简历。合作方资质仍归 Base-4，不因角色名称自动获得学校发布权。

### 页面与空间

校园连接页面和三维房间的“此地点的校友、学长支持与职业机会”共用真实 sceneId/entityId。只能绑定本校现有公共房间；点位不绕过登录、审核或角色权限。地点失效的条目停止公开，管理视图保留处理入口。该能力支持建筑/房间锚点；任意GIS点位及多场景调度仍需现有空间适配，不声称已提供通用GIS引擎。

## 技术与代码归属

| 部分 | 复用开源 | 本项目自研扩展 |
| --- | --- | --- |
| 身份、学校/组织角色 | Keycloak、PostgreSQL | 当前资格/角色复核、本人同意、审核与审计 |
| 接待会话 | Node、PostgreSQL；原有Hermes/模型适配 | 生命周期、隔离、期限、导出/删除、防重放、有界上下文 |
| 校友目录、支持预约 | PostgreSQL事务/索引、既有通知 | 名片状态、时间/容量规则、参与者隐私和管理页面 |
| 职业机会 | NodeBB原生正文/编辑/审核 | 结构化卡片、原生来源版本绑定、截止/链接/锚点与收藏 |
| 联系与空间 | Nakama、Three.js、既有联系人系统 | 显式联系授权和同一对象的页面/房间入口 |

没有另外部署一套CRM、身份或预约服务。开源许可证与固定版本沿用 `integrations/versions.json` 及原许可证文件；学校规则不是这些项目自带的现成成品模块。

## 运行与迁移

沿用 `docs/DEPLOYMENT-CONTAINERS.md` 和 `CAMPUS-START.md` 的全栈路径。新校园部署启用 `campusEnabled` / Base-3 后，`campus-network-001` 在现有版本迁移锁下新增表；不修改已应用迁移。现有实例先停写并完成全量备份，在新的目录/数据库命名空间演练恢复升级，保留原数据和旧源码包。管理员账号仍按原初始化/邀请流程配置。

新增入口：`/network.html`、`/reception-admin.html`；账号管理导航和公开房间已接入。无需更换现有模型、embedding或向量库，未配真实模型时继续明确显示“资料接待”。

## 验证与实际边界

对应脚本：`tests/reception-sessions.test.mjs`、`tests/reception.test.mjs`、`tests/network-live.mjs`、`tests/network-browser.mjs`、`tests/network-restore.mjs`。真实服务验证使用独立 `hdnetwork26` 的虚构账号及学校；浏览器使用同一台Windows上的新隔离上下文连接Ubuntu Docker。

新增数据表和接待权威状态已纳入七库备份；独立恢复比较行哈希，并验证恢复会话导出、跨人拒绝和模拟未来到期清理。恢复存储验证不等于新目标服务器全部服务已经上线。证据见 `evidence/network/ACCEPTANCE.md`；真实学校身份核验、导师履约、雇主真实性、真实SMTP/TLS、目标服务器资源和真实模型本轮对话不由自动化检查替代。P2地区/跨校社群与复杂交易继续暂缓。
